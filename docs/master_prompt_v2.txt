## 1. Tech Stack & Architecture

* **Android:** Kotlin, Jetpack Compose (Material 3), MVVM, Hilt, Coroutines/Flow.
* **Secure storage:** Jetpack DataStore encrypted with **Tink** (keys in Android Keystore). `EncryptedSharedPreferences` is deprecated — do NOT use. Supabase session must be persisted through this secure storage.
* **Local DB:** Room (Offline-first SSOT, exported schemas, explicit Migrations).
* **Background:** WorkManager (sync, local reminders).
* **Push:** Firebase Cloud Messaging (HTTP v1).
* **Backend:** Supabase (Postgres + RLS, Auth, Storage, Edge Functions in Deno, `pg_cron`, `pg_net` / Database Webhooks).
* **Web:** Static HTML + supabase-js on GitHub Pages (payment page, account deletion request page).
* **Build:** GitHub Actions builds all flavors. Separate Supabase projects for `dev` and `prod`.
* **Paradigm:** SaaS multi-tenancy, 1 central Supabase project, strict RLS isolation by `tenant_id`.
* **Money:** `bigint` rupiah in DB, `Long` in Kotlin. Never Float/Double.
* **Time:** `timestamptz` everywhere; display in device zone (WIB/WITA/WIT).

## 2. Identity, Roles & Security

* **Roles:** `SUPER_ADMIN` (system owner), `TENANT_ADMIN` (warung owner), `BRANCH_CASHIER`.
* **`memberships`** (user_id PK → auth.users, tenant_id, outlet_id nullable, role). Writable only by SECURITY DEFINER functions / service role.
* **Custom Access Token Hook** puts `tenant_id`, `role`, `outlet_id` into JWT claims. Client refreshes session after role changes.
* **RLS pattern** (cached per statement): `using (tenant_id = (select (auth.jwt()->>'tenant_id')::uuid))`. `SUPER_ADMIN` bypass via `(select auth.jwt()->>'role') = 'SUPER_ADMIN'` only where needed.
* **`tenant_id` is set by a BEFORE INSERT trigger** from the JWT. Client-sent `tenant_id` is ignored/overwritten.
* **Write paths:** `REVOKE INSERT/UPDATE/DELETE` on transactional tables from `authenticated`; all writes through RPCs. Every SECURITY DEFINER function uses `set search_path = ''` and checks the caller's role inside.
* **Registration:** requires real auth (Google Sign-In or email OTP). One tenant per owner account. Rate-limit `register_new_tenant`. Optional Play Integrity check against trial farming.
* **Cashier accounts:** created only via Edge Function `invite_cashier` (service role), which also writes the membership with `outlet_id`.
* **Storage:** private buckets, object path prefix `{tenant_id}/...`, access via signed URLs. Buckets: `payment-proofs`, `outlet-assets` (logo, merchant QRIS), `system-assets` (global QRIS).
* **Admin app:** biometric/PIN lock on open; all admin RPCs re-check `SUPER_ADMIN` server-side.
* **Webhooks → Edge Functions** authenticated with a secret header. FCM service account and all secrets in Supabase secrets, never in code or APK.
* **Obfuscation:** R8/ProGuard rules for all flavors.

## 4. Subscription Logic

* `access_until = greatest(trial_ends_at, coalesce(paid_until, '-infinity'))`
* `grace_until = access_until + grace_days`
* Derived status:
  * `TRIAL`: paid_until is null and now() <= trial_ends_at → full access
  * `ACTIVE`: now() <= access_until → full access
  * `GRACE`: now() <= grace_until → can still sell, red banner
  * `EXPIRED`: after grace → READ-ONLY (reports, history, export allowed; no new sales). Data never deleted.
* Trial = 30 days, set by `register_new_tenant`.
* Extension: `paid_until = greatest(now(), access_until) + make_interval(months => plan.months)`. Paying during trial keeps remaining trial; paying after expiry starts from approval date (never backdated).
* RPC **`get_entitlement()`** returns server_now, access_until, grace_until, status, pay_code, max_offline_days. Always server `now()`.

## 5. Pricing, Discounts & Plans (SUPER_ADMIN configurable)

* Base monthly price in `system_settings`. Durations 1 / 3 / 6 / 12 months (toggle each), discount % per duration, badge, optional `promo_ends_at`.
* Final price = `floor(normal_price * (1 - discount_pct/100) / 1000) * 1000`.
* RPC `upsert_plan`: retires the old version and inserts a new one. Rejects if the final price equals any plan that is active or retired within the last 180 days (show "harga bentrok").
* `pg_cron` daily: when `promo_ends_at` passes, retire the promo version and create the normal-price version.
* Price is locked at claim time (`plan_price_snapshot`): a promo chosen before it ended is honored.
* Example (reference only): Rp29.000/bln; 3 bln −5% = Rp82.000; 6 bln −10% = Rp156.000; 12 bln −20% = Rp278.000.

## 6. Payment Flow & Matching (manual verification)

**Flow:**
1. Tenant opens payment page (link from WA/email, never from the Play app), logs in with the same account.
2. Chooses duration → page shows ONE exact amount = plan price + pay_code (e.g. Rp278.137) with copy button and warning "Transfer PERSIS, SEKALI saja".
3. Pays via static QRIS or bank transfer. Optionally uploads proof + sender name → RPC `submit_payment` creates a `payment_confirmations` claim. Proof and sender name are OPTIONAL.
4. Webhook → Edge Function → FCM to admin app: "Pembayaran baru: {business_name} ({customer_code}) • Rp{amount} • {plan}".
5. Admin records the real money seen in bank mutation / QRIS merchant app into `incoming_payments` (QRIS: check the merchant app, because bank settlement is aggregated and net of MDR).
6. System decodes: `code = amount % 1000` → tenant; `base = amount - code` → plan (match any plan version within 180 days; or base divisible by monthly price = N months). Decoding is a SUGGESTION ONLY, never auto-approve.
7. Admin approves → RPC `approve_payment(incoming_payment_id, tenant_id, plan_id, note)` in ONE transaction with `FOR UPDATE`: ledger MATCHED, claim APPROVED, paid_until extended, CHURNED → LIVE if needed, `subscription_events` + `audit_logs` rows, FCM data message `ENTITLEMENT_UPDATED` to tenant devices.
8. `reject_payment(claim_id, reason)` with reason chips: nominal tidak sesuai, dana belum masuk, bukti tidak jelas, duplikat. Notify tenant.

**Rules:**
* `approve_payment` REQUIRES an `incoming_payments` row. No ledger row → cannot approve.
* `incoming_payments.claim_id unique` → one transfer activates once.
* `proof_sha256` duplicate → flag.
* Red flag when decoded code ≠ claimant's pay_code (e.g. tenant multiplied 3 × Rp29.137 = Rp87.411 → code 411 belongs to someone else).
* Several separate monthly transfers stack (each approval extends).
* Amount not matching any plan: admin chooses nearest lower plan + remainder to `credit_ledger`, or refund.
* Unknown money ("Uang Masuk Tak Dikenal"): ledger rows with status UNMATCHED stay listed until a tenant claims them; admin links them. Full audit trail.
* Payment page must always be reachable, also for CHURNED tenants, with a "Saya sudah transfer" claim even without a chosen plan.
* Payment terms shown on payment page: transfer exact amount; activation max 1×24 jam hari kerja; late payments are accepted; wrong amount/double payment → refund or extension balance.

## 7. Offline-First Sync & Expiry Enforcement

**Trusted time (device):**
* On every successful sync store (encrypted): server_now, grace_until, elapsedRealtime at sync, last_trusted_time.
* `trusted_now = server_now + (elapsedRealtime_now - elapsed_at_sync)`.
* After reboot (elapsedRealtime smaller): `trusted_now = max(System.currentTimeMillis(), last_trusted_time)`.
* If no successful sync for more than `max_offline_days` (7) → require one online check before new sales, even if subscription is active.

**Checkout gate:** before creating a sale: `trusted_now <= grace_until` else block sale and show read-only mode. Banners: yellow from H-7, red during GRACE.

**Sync engine (WorkManager):**
* Client-generated UUIDv7 IDs; BATCH upsert via RPC (`on conflict (id) do nothing` for orders) → retries are idempotent.
* Push: pending local rows in batches. Pull: delta by `updated_at > last_pulled_at` per table (products, outlets, settings, plans status, void decisions).
* Soft deletes (`deleted_at`) propagate to all devices; hard delete only as later purge.
* Conflict policy: server wins for master data; orders immutable after creation (changes only via `void_requests`).
* Server NEVER rejects synced orders: `created_at <= grace_until` → `sync_flag='OK'`, else stored with `sync_flag='FLAGGED'` for audit.
* Server-side subscription check applies only to online-created operations, never to the sync of historical sales.

## 8. Notifications & Reminders

**Tenant (in-app only, status text, no price/link):**
* Server: `pg_cron` hourly → `send_reminders` Edge Function at configured hour; schedule H-7, H-3, H-2, H-1, H0, daily during GRACE, on EXPIRED; dedupe via `reminder_log`.
* Local fallback: daily WorkManager computes from cached grace_until (works offline); skip if server push for that day arrived.
* Approved/rejected payment push. `POST_NOTIFICATIONS` permission (Android 13+).
* Example text: "Langganan berakhir 3 hari lagi (12 Des). Kode pelanggan: WRG-7K3P."

**Admin:**
* Push on new claim; daily push "{n} tenant perlu diingatkan hari ini"; next-morning push for unsent queue items.
* `build_reminder_queue()` via `pg_cron` hourly, runs when WIB hour = `run_hour` and enabled: tenants with access_until at H-`days_before` or in GRACE (LIVE only) → `wa_reminder_queue` with suggested amount (best plan incl. pay_code).
* "Antrean WA" screen: tap "Kirim WA" → opens `https://wa.me/{phone}?text={urlencoded template}` → mark SENT; "Lewati" → SKIPPED.
* Template placeholders: {nama_usaha}, {kode}, {tanggal}, {nominal}, {promo_terbaik}, {link}.

**Tenant lifecycle:**
* `pg_cron` daily: EXPIRED longer than `auto_churn_after_days` → CHURNED (churn_reason 'AUTO_EXPIRED'); open claims → CANCELLED; removed from queue/active lists.
* Manual "Tandai Tidak Lanjut" with reason. Archive tab in admin. Approved payment revives to LIVE.
